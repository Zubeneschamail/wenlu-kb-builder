## S03｜鹭桥订单平台：背景与个人职责

鹭桥订单平台为企业采购业务提供统一的订单入口。用户提交订单后，可以查询订单状态和明细；订单创建成功会触发后续通知。

项目团队共 7 人，包括 1 名技术负责人、3 名后端开发、2 名前端开发和 1 名测试。林舟是 3 名后端开发之一。

林舟具体负责：

1. 订单列表和订单详情接口。
2. 热点订单详情的 Redis 缓存。
3. 订单创建接口的重复请求识别。
4. 查询链路的慢 SQL 排查和压测结果整理。

技术负责人决定系统整体架构。支付渠道接入由另一名后端开发负责；基础设施部署由公司平台组负责。林舟没有负责支付渠道实现、前端页面或数据库分库分表。

核心实体为 `purchase_order`，主要字段包括 `tenant_id`、`order_no`、`status`、`created_at`。查询接口先校验用户所属租户，再在 SQL 中使用 `tenant_id` 限定数据范围。

## S04｜鹭桥订单平台：列表查询优化

订单列表接口为 `GET /api/orders`，支持按租户、订单状态和创建时间查询。原实现逐条查询每个订单的扩展信息，存在 N+1 查询；部分高频查询条件也没有匹配的联合索引。

林舟先通过慢查询日志定位 SQL，再使用执行计划确认扫描范围。修改包括：

- 将逐条扩展查询改为分页结果范围内的批量查询。
- 为主要筛选路径增加联合索引 `(tenant_id, status, created_at, id)`。
- 深分页场景使用上一页最后一条记录的创建时间和 ID 继续查询，减少大偏移量扫描。
- 页面仍按每页 20 条返回，并明确保持排序的一致性。

模拟压测条件：预生产环境、订单表约 300 万行、固定测试租户和请求分布，预热后在 1000 RPS 的负载下持续测试 30 分钟。

在上述相同条件下，订单列表接口的 P95 延迟从 420 毫秒降至 165 毫秒。该指标来自预生产压测，不是生产全站平均响应时间，也不能据此推导生产系统的峰值 QPS。

优化结果不能单独归因于 Redis：这次列表优化主要来自批量查询、索引调整和分页方式；下一节的 Redis 缓存用于订单详情。

## S05｜鹭桥订单平台：详情缓存与请求幂等

订单详情接口为 `GET /api/orders/{order_no}`。热点详情使用 cache-aside 方式读取：先查 Redis，未命中时读取 MySQL，再回填缓存。

缓存键包含租户和订单号，示例为 `order:detail:{tenant_id}:{order_no}`。缓存有效期为 120 秒，并增加 0 至 30 秒的随机抖动。订单状态更新在数据库事务提交后删除对应缓存。该模块接受短时间的最终一致性，不宣称任意并发情况下都能立即读到最新状态；明确需要最新状态的确认操作直接查询数据库。

创建订单接口为 `POST /api/orders`。客户端传入 `request_id`，服务端在数据库中对 `(tenant_id, request_id)` 建立唯一约束，并记录对应的订单号。同一租户重复提交同一请求时，返回已经创建的订单结果。

Redis 可用于减少短时间重复请求带来的数据库压力，但最终的幂等保障依赖数据库唯一约束。这个机制处理的是重复创建订单，不是支付扣款幂等。

## S06｜星舟工单平台：背景与技术取舍

星舟工单平台服务于公司内部运维流程，支持创建工单、分配处理人、状态流转、超时提醒和操作审计。

项目团队共 5 人，包括 1 名技术负责人、2 名后端开发、1 名前端开发和 1 名测试。林舟负责工单后端接口、提醒任务、审计事件和相关故障排查；他没有负责前端页面，也没有独立设计整个平台。

创建工单接口为 `POST /api/tickets`，状态流转接口为 `POST /api/tickets/{id}/transitions`。工单状态包括待处理、处理中、待确认、已关闭。

系统以 MySQL 保存工单和审计记录，以 RabbitMQ 分发异步提醒。Redis 在本项目中用于缓存组织目录信息和提醒任务的短期去重，不承担鹭桥订单详情缓存的职责。

团队选择保留模块化单体架构，没有拆成大量微服务。原因是团队规模小、业务边界还在调整，而且当时的主要问题是任务处理方式，尚未形成必须独立扩缩容的压力。整体决策由技术负责人组织讨论后确定，林舟参与提醒模块的方案评审。

## S07｜星舟工单平台：提醒任务优化

最初的提醒任务按顺序处理到期工单：逐条查询接收人，再同步调用通知服务。通知接口响应较慢时，会拖延整批任务。

林舟把流程改为批量读取到期工单和接收人信息，再把提醒事件投递到 RabbitMQ，由 4 个消费者并行处理。事件包含 `event_id` 和 `ticket_id`；消费者记录处理结果，识别重复投递。

提醒优化的模拟测试条件：预生产环境，固定 1 万条待提醒工单，使用相同的通知服务模拟响应分布，分别重复测试 5 次。

整批提醒处理完成时间的中位数从 18 分钟降到 5 分钟。这不是用户创建工单接口的响应时间，也不是 P95 延迟。

系统按至少一次投递设计，消费者需要处理重复事件。没有宣称消息只投递一次，也没有使用 Redis 作为唯一可靠的处理记录。

## S08｜星舟工单平台：一次通知遗漏故障

2025 年 12 月，星舟工单平台出现少量工单状态已经更新、提醒却没有发出的情况。

旧代码先提交数据库事务，再发送 RabbitMQ 消息。如果事务提交后进程异常退出，工单更新已经保存，但消息还没有发出，形成遗漏窗口。

林舟通过应用日志、工单更新时间和消息记录之间的差异定位该问题，并实现修复：

1. 在更新工单的同一个数据库事务内，将待发送事件写入 outbox 表。
2. 后台投递任务扫描尚未发送的事件并投递消息。
3. 失败后按退避策略重试；连续失败的事件保留记录并触发告警。
4. 消费者根据 `event_id` 进行幂等处理，允许消息重复投递。

方案由技术负责人审核后发布。模拟故障注入验收覆盖“数据库提交后进程退出”和“消息已发出但发送状态尚未更新”两种情形：前者可由后续任务补发，后者可能重复投递，但不会重复执行已完成的事件处理。

资料没有记录该故障影响的确切工单数量、持续分钟数或经济损失，因此不能据此生成这些数字。
